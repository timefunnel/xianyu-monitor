## 1. 结论速览（TL;DR）

| # | 结论 | 对我们的意义 |
|---|---|---|
| 1 | **可靠推送这块，全网最干净的参考实现是 Alertmanager**，不是任何「监控商品」的项目。它的 `RetryStage` + `nflog` 组合把「不能丢也不能重复」拆成了清晰的三段：**去重判断 → 无限重试到成功 → 成功后才写投递日志**。 | 我们该抄的是它的**结构**，不是它的代码（Go）。 |
| 2 | **绝大多数同类工具根本不做可靠投递**。changedetection.io（34.5k★）把实际投递交给 Apprise；Apprise 的默认重试次数是 **`service_retry = 0`**；Uptime Kuma 的 `notification.js` 里没有重试循环。 | 「推送不能丢」在开源监控圈**是稀缺能力**。做对了就是差异化。 |
| 3 | **我们自己已经有一个真实的丢推送缺陷**（不是理论风险）：`src/monitor.mjs:482` 用 `results.some(r => r.ok)` 判断是否记账，**多渠道路由下会永久丢掉失败那个渠道的推送**。 | 这是本次调研中**最高优先级**的修复项，见 §5.1。 |
| 4 | **`src/store.mjs` 的原子写（临时文件 + rename）+ 损坏备份 + TTL/LRU 裁剪，已经优于绝大多数同类项目**，不需要重做。 | 省下工作量，把力气放到别处。 |
| 5 | **Bloom 过滤器不适合我们**。假阳性 = 永久漏报，对「不能漏」的监控是错误工具。**重复推送优于漏报**，这与 at-least-once 语义一致。 | 体积控制继续用 TTL + 数量上限。 |
| 6 | **「界面把别处改动回滚」的正解不是「小心一点」，而是给配置加版本号做 CAS**，冲突时返回 409 让界面重载。我们现在的「从磁盘重读、只改一个键」是对的但不完整。 | 见 §2.5、§5.3。 |
| 7 | **Prometheus 对我们这种单实例自托管工具，性价比低于「任务心跳告警」**。healthchecks.io 的 `Period + Grace Time` 模型用 20 行代码就能实现，直接解决「任务僵死没人知道」。 | 见 §2.4、§5.2。 |
| 8 | **许可证：本次调研的参考实现全部是宽松许可证**（Alertmanager/ntfy/gatus Apache-2.0，Uptime Kuma/Huginn/gotify MIT，Scrapy/Healthchecks BSD-3，Apprise BSD-2，RSS-Bridge Unlicense）。**唯一要避开的是 RSSHub（AGPL-3.0）**。 | 可以直接抄代码，不必只看思路。 |

## 2. 值得借鉴的架构设计

### 2.1 可靠推送：durable outbox / 幂等键 / at-least-once

#### 2.1.1 🟢 Alertmanager —— 这是「教科书」，我把它的投递流水线读完了

Alertmanager 的 notify pipeline 由三个阶段串成，顺序本身就是设计：

```
DedupStage  →  RetryStage  →  SetNotifiesStage
（要不要发）   （发到成功）     （记下发过了）
```

**① 投递日志写在投递成功之后 —— 这就是 at-least-once 的来源**

`notify/set_notifies_stage.go` 是 pipeline 的**最后一环**，只有在 RetryStage 没报错时才会执行。这意味着：**进程崩溃 → 日志没写 → 下轮重新通知 → 最坏情况是重复，绝不会是漏报。**

这一点我核到了**两处原文**，是整个报告最硬的一条证据。

**第一处 —— pipeline 的组装顺序**（📎 `notify/notify.go` L262-267）：
```go
stages := []Stage{
	NewClusterWaitStage(wait),
	NewDedupStage(&integrations[i], notificationLog, recv),
	NewRetryStage(integrations[i], name, metrics, recorder),
	NewSetNotifiesStage(notificationLog, recv, ff),
}
```

**第二处 —— 阶段遇到错误立刻中断，后续阶段不执行**（📎 `notify/notify.go` L326-346）：
```go
// execStages runs the given stages in order. It stops early once no alerts are
// left, unless continueWhenMuted is set and a mute stage has recorded the
// alerts it removed.
func execStages(ctx context.Context, l *slog.Logger, stages []Stage, continueWhenMuted bool, alerts ...*alert.Alert) (context.Context, []*alert.Alert, error) {
	var err error
	for _, s := range stages {
		if len(alerts) == 0 {
			...
		}

		ctx, alerts, err = s.Exec(ctx, l, alerts...)
		if err != nil {
			return ctx, nil, err      // ← RetryStage 报错 → SetNotifiesStage 不会执行 → 不写投递日志
		}
	}
	return ctx, alerts, nil
}
```

**推论（这就是可抄的全部）**：把「**记录已投递**」放在「**投递成功**」之后、并且让「投递失败」直接短路掉「记录」这一步，你就**免费获得了 at-least-once**。反过来，先记账再投递，就是 at-most-once（会漏报）。**顺序即语义。**

`nflog` 的日志键是「组 + 接收器」，而不是「告警本身」：

> 📎 `nflog/nflog.go` L178-181
> ```
> // For now we only store the most recently added log entry.
> // The key is a serialized concatenation of group key and receiver.
> ```

**这条对我们直接致命相关**：Alertmanager 把 **receiver（通知渠道）当作去重键的一部分**。我们按「商品 ID」记账，没把渠道算进去 —— 这就是 §5.1 那个 bug 的根因。

**② 无限重试，直到上下文取消；用 verdict 区分「可重试」和「不可重试」**

> 📎 `notify/retry_stage.go` L32-33
> ```go
> // RetryStage notifies via passed integration with exponential backoff until it
> // succeeds. It aborts if the context is canceled or timed out.
> ```

> 📎 `notify/retry_stage.go` L110-111
> ```go
> // backoff/v5's ExponentialBackOff never returns Stop from NextBackOff, so
> // we retry indefinitely until the context is canceled.
> ```

注意它是**无限重试**（不设 maxAttempts），靠「上下文超时」和「不可恢复错误」两个出口跳出。这是有意的：漏报不可接受，重复可接受。

**③ 通知器必须回答「这次失败值不值得重试」**

> 📎 `notify/notify.go` L112-114
> ```go
> // Notifier notifies about alerts under constraints of the given context. The
> // returned verdict tells whether the notification succeeded and, if it did not,
> // whether the failure is recoverable.
> ```

> 📎 `notify/notify.go` L61-71
> ```go
> // NotifyVerdict is the outcome of a notification attempt.
> type NotifyVerdict struct {
> 	err        error
> 	retry      bool
> 	retryAfter time.Duration
> 	...
> }
>
> // Retry returns the verdict for a notification that failed with err and is
> // worth another attempt. A zero retryAfter leaves it to the retry logic to
> // pick the delay before that attempt.
> ```

> 📎 `notify/notify.go` L81-83
> ```go
> // Unrecoverable returns the verdict for a notification that failed and can't
> // be retried.
> ```

对应到我们的场景：`HTTP 429` / 连接超时 → **可重试**；`HTTP 401`（token 过期）/ `400`（payload 格式错）→ **不可重试，直接告警**。我们现在 `src/notify.mjs:319-323` 的 `toResult` 把**所有非 2xx 一律当失败**，没有这个区分。

**④ 退避时间从「尝试结束」起算，且尊重 `Retry-After`**

> 📎 `notify/retry_stage.go` L159-161
> ```go
> // Back off from the end of the attempt, not from its start, so a
> // slow failure doesn't eat into the wait.
> tick.Reset(max(b.NextBackOff(), verdict.Delay()))
> ```

`max(自身退避, verdict.Delay())` —— 即**服务端要求的 `Retry-After` 优先**，但不得低于自身的指数退避。这是一行代码解决的经典问题。

**⑤ 去重阶段：靠投递日志判断「该不该发」**

> 📎 `notify/dedup_stage.go` L30-31
> ```go
> // DedupStage filters alerts.
> // Filtering happens based on a notification log.
> ```

`dedup_stage.go` 的 `needsUpdate()` 逻辑（我读了 L52-96）区分了：首次通知 / 组内新增 / 全部恢复 / 新增恢复 / **重复间隔到期** / 无需通知。最后一种 `ReasonRepeatIntervalElapsed` 是「同一件事过了 repeat 间隔还没好，再提醒一次」—— 可用于我们的「风控持续未解除，每 N 小时再提醒一次」。

**⑥ 日志有 TTL 和定期维护（体积控制的成熟做法）**

> 📎 `nflog/nflog.go` L321
> ```go
> 	Retention time.Duration
> ```

> 📎 `nflog/nflog.go` L189-190
> ```go
> // MaintenanceFunc represents the function to run as part of the periodic maintenance for the nflog.
> // It returns the size of the snapshot taken or an error if it failed.
> ```

即：**日志有保留期 + 定期 maintenance（GC + 快照）**，不是无限增长。这一点和我们 `store.mjs` 的 `retentionDays` + `limit` 裁剪思路一致 ✅。

#### 2.1.3 🟡 Apprise 的一个值得抄的小设计：`optional` 渠道

`apprise/plugins/base.py` L229-259 定义了一个「nice to have」概念：

> 📎 `apprise/plugins/base.py` L229-234
> ```python
> # When set to True, a delivery failure for this individual service is
> # silently absorbed by all three dispatch paths (sequential, thread-pool,
> # and asyncio coroutine).  The overall notify() / async_notify() call
> # still returns True even if this particular endpoint could not be
> # reached, provided that every *required* (non-optional) service in
> # the same batch succeeded.
> ```

> 📎 `apprise/plugins/base.py` L249-254
> ```python
> #   - Retries are still performed up to the configured retry count
> #     before a service is considered to have failed.  The optional flag
> #     only fires *after* all retry attempts have been exhausted without
> #     a successful delivery.  In other words, optional does not bypass
> #     the retry loop -- it only changes the meaning of the final result.
> ```

**对我们的直接启发**：把通知渠道分成 **required（必须送达，失败要重试+告警）** 和 **optional（尽力而为，失败只记日志）**。比如 Telegram 是 required，某个自定义 webhook 是 optional。这让「部分渠道失败」有明确的、由用户配置的语义，而不是我们现在 `some(ok)` 这种一刀切。

#### 2.1.4 🟡 闲鱼生态里唯一做对 outbox 的项目

`LENKIN233/xianyu-monitor-skill`（MIT，18★）—— 已有调研报告记录过它的设计（本次未重复下载其源码，标记为 🟡，原文转引自 `docs/闲鱼开源项目调研报告.md` §5.2）：

> 新商品会和 seen ID 在同一原子提交中写入 durable outbox；适配器通过 `task outbox list` 读取，复用 `idempotency_key`，仅在外部投递确认成功后执行 `task outbox ack`。

> 若发送超时、发送中取消或本地 ack 无法确定，事件保留并返回 `possible_duplicate: true`；**未收到响应不等于未送达，不要盲目重试。**

> 重复通知优于已提交 ID 导致的永久漏报。

这三点和我们下面要抄的 Alertmanager 结构完全一致，可以互相印证。

#### 2.1.5 🟢 我们自己的现状（读了 `src/monitor.mjs` / `src/notify.mjs` / `src/store.mjs`）

**已有的、值得保留的：**
- 全渠道失败 → **不记 seen** → 下轮重试（`src/monitor.mjs:489-491`）。方向正确 ✅
- 静默期命中只记账不推送，用 `pushed:false` 区分（`src/monitor.mjs:459-470`）。语义清晰 ✅
- 超过 `maxPerCycle` 的命中聚合成一条汇总推送（`src/monitor.mjs:494-509`）。避免刷屏 ✅

**三个具体缺口：**

| 缺口 | 位置 | 后果 |
|---|---|---|
| **① 按商品记账，不按渠道记账** | `src/monitor.mjs:482` `if (results.some((result) => result.ok))` → `store.add(item.id)` | 多渠道路由下，失败的那个渠道**永久收不到这条**。见 §5.1。 |
| **② 没有持久化 outbox** | 全流程在内存里，`sendAll` 成功后才 `store.save()` | 若在 `sendAll` 成功后、`store.save()` 前崩溃 → 该条不算 seen → **重复推送**（可接受）；但若渠道侧「已收到但响应超时」，我们记为失败 → 下轮**重复推送**。方向安全，可惜没有 `possible_duplicate` 这个显式信号。 |
| **③ 失败告警本身也不可靠** | `src/monitor.mjs:300` 的 `#notify(...)` 走的还是同一个 `sendAll` | 「登录失效」「风控被拒」这类**最需要送达**的告警，一旦渠道抖动就丢了，而且没有二次重试。 |

#### 2.1.6 可抄的 outbox 设计（综合 Alertmanager + LENKIN233）

**表结构**（单文件 JSON 或 SQLite 均可，字段照抄）：

```
outbox:
  id            自增/ULID
  item_id       商品 ID
  channel       渠道标识（telegram / dingtalk / ...）   ← 关键：渠道进键
  task          任务名（命中来自哪个任务）
  payload       渲染好的消息体（title/body/url）
  idem_key      sha1(item_id + ':' + channel + ':' + task)  ← 幂等键
  status        pending | sending | sent | failed | unrecoverable
  attempts      已尝试次数
  next_attempt_at   下次可尝试时间（退避调度用）
  last_error    最后一次错误（截断 200 字）
  created_at / updated_at
```

**核心不变量（抄 Alertmanager 的顺序）：**

1. **入队 = 命中判定成功的同一时刻**。命中 → 写 `outbox(pending)` + 写 `seen`，**同一个原子提交**（`store.save()` 一次写完两者）。
2. **投递循环**：取 `status=pending AND next_attempt_at <= now`，按渠道**独立**投递。
3. **只有该渠道投递成功，才把这一行标 `sent`** —— 而不是把商品 ID 标 seen。
4. **`seen` 与 `outbox` 的关系**：`seen` 只负责「下一轮不要重复命中」，`outbox` 负责「已经命中的别丢」。两者分离。
5. **重试策略**：指数退避 + 抖动；`429`/超时/5xx → 可重试；`401`/`400` → 标 `unrecoverable` 并**立即告警**。
6. **幂等**：投递前按 `idem_key` 去重；即便重复投递，业务侧也不该重复告警（至少日志里能识别）。
7. **TTL**：`sent` 的行保留 7~30 天后清理；`unrecoverable` 的行**保留并单独暴露**在界面里（这是人工介入队列）。

### 2.2 去重与状态持久化

#### 2.2.1 🟢 Scrapy：二进制指纹文件 + 明确承认会无限增长

> 📎 `scrapy/dupefilters.py` L86-89
> ```
> When using :setting:`JOBDIR`, seen fingerprints are tracked in a binary
> file named :file:`requests.seen` in the :ref:`job directory <job-dir>`,
> where each fingerprint is stored as its big-endian, 2-byte length followed
> by the fingerprint itself.
> ```

实现细节（读了 L33-42、L100-123）：每条指纹是 **2 字节大端长度前缀 + 指纹内容**，启动时全部读进 `set[bytes]`，新增时追加写文件。

**值得抄**：长度前缀的自描述二进制格式，追加写、天然可恢复、不需要 parse 整个 JSON。
**不值得抄**：**它没有 TTL 也没有上限**，记录永远增长。Scrapy 是短生命周期的爬取任务，我们是**常驻进程**，必须有裁剪 —— 这一点我们 `store.mjs` 的 `prune()` 已经做得比它好。

#### 2.2.2 🟢 我们自己的实现（`src/store.mjs`，读了全文 161 行）

已经具备的能力，**不需要重做**：

| 能力 | 实现 | 评价 |
|---|---|---|
| 原子写 | `writeFileSync(temp)` + `renameSync(temp, this.file)`（L150-152） | ✅ 正确，进程被杀不会留半截文件 |
| 版本字段 | `STATE_VERSION = 1`，不匹配就抛错（L57-59） | ✅ 有向前兼容意识 |
| 损坏自愈 | 解析失败 → 备份为 `.corrupt-<ts>` 并以空表启动（L67-72） | ✅ 比多数项目做得好 |
| 双层裁剪 | `retentionDays`（时间）+ `limit`（数量，按时间戳淘汰最旧）（L101-116） | ✅ 正是我们需要的 |
| 脏标记 | `dirty` 标志，无变化不重写（L146） | ✅ 避免每分钟写盘 |
| 计数持久化 | `totals` 跨重启延续（L132-139） | ✅ 解决了「重启后界面自相矛盾」 |

**唯一可以加的**：`fsync`。`rename` 保证原子性，但不保证数据已落盘 —— 掉电场景下可能丢最后一批。对监控场景，丢一批 = 可能重复推送（安全方向），所以**优先级低**。

#### 2.2.3 体积控制方案对比（结论：TTL + 上限最适合我们）

| 方案 | 机制 | 体积 | 漏报风险 | 重复风险 | 适合我们？ |
|---|---|---|---|---|---|
| **TTL（按时间）** | 超过 N 天删除 | 中 | **有**：N 天前上架、N 天后又被搜到的商品会重推 | — | ✅ **作为第一层**（同商品短期内不会重新出现，30 天足够） |
| **LRU / 数量上限** | 超过 M 条淘汰最旧 | 硬上限 | 有（同上，但可控） | — | ✅ **作为第二层**（保证文件不会撑爆磁盘） |
| **布隆过滤器** | 位数组 + k 个哈希 | 极小 | ❌ **假阳性 = 永久漏报，且无法删除元素** | 无 | ❌ **不适合**。对「不能漏」的监控是错误工具 |
| **SQLite + 索引** | 持久化 + `DELETE WHERE ts < ?` | 中 | 同 TTL | — | 🟡 值得考虑（见下） |
| **计数型布隆 / Cuckoo** | 支持删除 | 小 | 仍有假阳性 | — | ❌ 同上 |

**关键判断**：布隆过滤器把「不存在」误判为「存在」时会**永久漏掉一条命中**，而且它**不支持删除**（我们 `prune()` 依赖删除）。它的省空间优势（相对几千条 ID 的 JSON）在我们的量级上毫无意义 —— `store.mjs` 默认 `limit=20000`，20k 条 ID 的 JSON 大约 500KB~1MB，完全不构成问题。

**记录体积参考**：`limit: 20000` + `retentionDays: 30` 的组合下，状态文件上限约 1MB，每次 `save()` 全量重写。如果实测 `save()` 变慢（>10ms），再考虑迁移到 SQLite 增量写。

#### 2.2.4 崩溃可恢复性的三个层次

| 层次 | 手段 | 我们是否需要 |
|---|---|---|
| L1 不产生半截文件 | 临时文件 + `rename` | ✅ **已有** |
| L2 数据真的落盘 | `fsync(fd)` 后再 `rename` | 🟡 可选（丢数据方向安全） |
| L3 可从任意崩溃点重建 | append-only WAL / SQLite | 🟡 量大了再说 |

**入队顺序的一个细节**（值得写进代码注释）：先写 `seen` 再投递，还是先投递再写 `seen`？
- **先写 outbox（含 seen），再投递** → 崩溃时可能丢投递（因为已经入队但没发）→ 但我们有 outbox，重启后会补发 ✅
- 这正是「事务性发件箱」的意义：**把『记录』和『待发』放进同一个事务，把『发送』放到事务外由重试机制保证**。

### 2.3 限流与退避

#### 2.3.1 🟢 Scrapy AutoThrottle：根据服务端延迟自适应（公式值得抄）

> 📎 `scrapy/extensions/throttle.py` L102-127（原文，含注释）
> ```python
> def _adjust_delay(self, slot: Slot, latency: float, response: Response) -> None:
>     """Define delay adjustment policy"""
>
>     # If a server needs `latency` seconds to respond then
>     # we should send a request each `latency/N` seconds
>     # to have N requests processed in parallel
>     target_delay = latency / self.target_concurrency
>
>     # Adjust the delay to make it closer to target_delay
>     new_delay = (slot.delay + target_delay) / 2.0
>
>     # If target delay is bigger than old delay, then use it instead of mean.
>     # It works better with problematic sites.
>     new_delay = max(target_delay, new_delay)
>
>     # Make sure self.mindelay <= new_delay <= self.maxdelay
>     new_delay = min(max(self.mindelay, new_delay), self.maxdelay)
>
>     # Dont adjust delay if response status != 200 and new delay is smaller
>     # than old one, as error pages (and redirections) are usually small and
>     # so tend to reduce latency, thus provoking a positive feedback by
>     # reducing delay instead of increase.
>     if response.status != 200 and new_delay <= slot.delay:
>         return
>
>     slot.delay = new_delay
> ```

**三个可直接抄的点：**

1. **用响应延迟反推「安全的请求节奏」**：`target_delay = latency / target_concurrency`。闲鱼搜索接口变慢，往往就是风控在加严的**前兆**。我们现在只按固定 interval + 抖动，没有用延迟做反馈信号。
2. **取平均而非直接跳到目标**：`new_delay = (slot.delay + target_delay) / 2.0` —— 避免单次抖动导致节奏剧烈震荡。
3. **错误响应不得降低延迟**（L120-125）。注释点出了一个真实的**正反馈陷阱**：错误页/重定向页体积小、响应快，如果按延迟自适应就会**越出错越快**，直接把自己打进封禁。**这条对我们的价值最高** —— 我们的退避逻辑只在 `catch` 里起作用，没有覆盖「HTTP 200 但内容是风控页」的情况。

#### 2.3.2 🟢 got：完整的单行退避公式 + `Retry-After` 的正确处理

> 📎 `sindresorhus/got` `source/core/options.ts` L630
> ```
> Delays between retries are calculated with
> `Math.max(1, Math.min((2 ** (attemptCount - 1)) * 1000, backoffLimit) + noise)`,
> where `attemptCount` starts at 1 and `noise` is the randomized retry noise.
> Setting both `backoffLimit` and `noise` to `0` requests an immediate retry;
> returning `0` from `calculateDelay` still aborts the retry.
> ```

> 📎 同文件 L653
> ```
> __Note:__ If [`Retry-After`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Retry-After)
> header is greater than `maxRetryAfter`, it will cancel the request.
> ```

还有几个工程细节值得抄（L635、L637）：
- 延迟超过 Node 的定时器上限（`2_147_483_647` ms）**直接放弃重试**而不是溢出成立即重试。
- `enforceRetryRules` 默认 `true`：**先按 limit/methods/statusCodes/errorCodes 判断允许重试，再调用 `calculateDelay`**。

**AWS 的 Full Jitter**（⚪ 未在本次调研中打开原始文章核实，属通行知识）：
```
sleep = random_between(0, min(cap, base * 2 ** attempt))
```
对比我们现在的 `Math.random() * task.jitterSeconds`（`src/monitor.mjs:307`）—— 我们只是**在固定间隔上加正向抖动**，退避部分 `cooldownSeconds * 2`（L269-272）**没有抖动**。这意味着多个任务同时失败时会在同一时刻集体重试（惊群）。

**建议**：退避值本身也加抖动，即
```js
cooldownSeconds = Math.min(cooldownSeconds * 2, maxBackoff) * (0.5 + Math.random() * 0.5)
```

#### 2.3.3 跨任务 / 跨进程的速率控制

| 场景 | 方案 | 说明 |
|---|---|---|
| **单进程、多任务** | **全局最小间隔闸**（我们已有）+ 令牌桶 | 令牌桶更适合「允许突发但限制平均」；全局最小间隔更适合「严格均匀」。**我们的场景（每任务每轮恰好 1 次请求）用全局闸是对的**，不必换令牌桶。 |
| **多进程 / 多实例** | 需要**进程外**协调：Redis 令牌桶、文件锁 + 时间戳、或独立的「请求代理」进程 | 我们目前是单进程（README 明确「单进程」），**暂时不需要**。但若将来上多账号并行，这是第一个要解决的地方。 |

**令牌桶参考实现**：`golang.org/x/time/rate`（BSD-3）、npm `bottleneck`（MIT）🟡。对我们的量级属过度设计。

#### 2.3.4 被平台限流/拒绝后的优雅降级阶梯

综合 Alertmanager 的 verdict 机制 + 我们已有的错误分类（`src/monitor.mjs:259-296`，**这块我们已经做得相当好**，有 `throttled` / `risk-control` / `denied` / `auth` / `filters-not-applied` 的区分且各自有不同冷却策略），建议的完整阶梯：

| 级别 | 触发条件 | 动作 | 我们的现状 |
|---|---|---|---|
| L0 正常 | 200 + 正常内容 | 正常间隔 | ✅ |
| L1 单次失败 | 网络错误 / 5xx | 指数退避 1 次，抖动 | ✅ 已有 |
| L2 限流 | 429 / `throttled` | 直接进最长冷却（**不做小步加倍**） | ✅ **已有且注释解释了原因**（L259-261） |
| L3 风控拒绝 | `risk-control` / `denied` | 长冷却 + **立即告警要人工介入** | ✅ **已有**（L262-267、L292-304） |
| L4 熔断 | 连续 N 次风控 | **暂停整个任务**（而非继续按间隔撞墙）+ 界面上显示「已熔断」 | 🟡 部分有（冷却计入了 `waitSeconds`），但没有「暂停」这个显式状态 |
| L5 全局熔断 | 多个任务同时风控 | 暂停**所有**任务，等人工 | ❌ 缺。这是一个真实的缺口：多任务同时被风控时，我们仍会各自按各自的冷却去试 |
| L6 半开探测 | 冷却结束后 | **单任务、单次**试探，成功才恢复正常间隔 | 🟡 现在的做法是直接用正常间隔重试，不是「单次试探」 |

**其中 L3 的注释质量值得一提**（`src/monitor.mjs:262-265`）：
> `// 风控验证在自动化窗口里**过不了**（baxia 会认出自动化环境），重试多少次都没用，`
> `// 反而会让风控更严。所以长时间退避，等人工用普通 Chrome 打开这个 profile 处理。`

这是**基于实测知识**的降级策略，比 Alertmanager 的通用退避更贴合场景。**保留它**。

### 2.4 可观测性

#### 2.4.1 日志分级与环形缓冲

我们已有：`src/logger.mjs` + 结构化任务级日志 + Web 控制台的 **SSE 实时日志**（`src/server.mjs`）。这是 `Uptime Kuma` / `changedetection.io` 同级甚至更好的形态。

**唯一建议**：给日志加「**每任务最近 N 条环形缓冲**」，让界面刷新后能立刻看到历史而不是空白。内存中固定大小的环形数组即可，不需要落盘。

#### 2.4.2 心跳 / 健康检查：对我们性价比最高的一项

`healthchecks.io`（10.4k★, BSD-3-Clause）的模型只有两个参数，我认为**直接抄**：

> 📎 [healthchecks.io — Configuring Checks](https://healthchecks.io/docs/configuring_checks/)
> - **Period** is the expected time between pings.
> - **Grace Time** is the additional time to wait before sending an alert when a check is late. Use this parameter to account for minor, expected deviations in job execution times.

> 📎 同文档（Cron 模式，说明「按时」比「按间隔」更强）
> This monitoring mode ensures that jobs run **at the correct time** and not just at the correct time intervals.

**为什么这个对我们最重要**：我们目前所有的告警都是**在 catch 里触发**的。也就是说 —— **如果一个任务悄无声息地卡住了**（比如 `await fetch` 永不返回、事件循环被某个同步操作阻塞、调度器的定时器被吞掉），`catch` 永远不会执行，**我们不会收到任何告警，界面上也看不出异常**（因为 `cycles` 也不涨，但没人盯着看）。

**心跳模型直接覆盖这个盲区**：
- 每个任务记录 `lastCycleCompletedAt`。
- 一个独立的轻量检查（每 30s）扫描所有任务：若 `now - lastCycleCompletedAt > intervalSeconds + graceSeconds` → 判定「错轮」→ 告警。
- 告警同样走 at-least-once（因为它是「该来的没来」，天然幂等）。

`healthchecks.io` 还提供 **`/badge/...` 状态徽章**，可以在 README 里放一个「本机监控是否还活着」的图 —— 对自托管项目是不错的用户可见信号。🟡

#### 2.4.3 Prometheus：值不值得加？

| 维度 | 判断 |
|---|---|
| **成本** | `prom-client`（Apache-2.0）+ 一个 `/metrics` 端点，约 **50~100 行**。`collectDefaultMetrics()` 能免费拿到事件循环延迟、GC、活跃句柄、Node 版本。 |
| **收益** | 需要**长期趋势**（命中率随时间变化、请求延迟漂移、退避次数趋势）和**Grafana 大盘**时才有价值。 |
| **我们的场景** | 单进程、单实例、自托管、已经有一个 Web 控制台 + 命中历史。**控制台已经覆盖了 90% 的「看一眼」需求。** |
| **结论** | 🟡 **可以加，但不是性价比最高的**。优先做 §2.4.2 的心跳告警。若加，最小指标集见下。 |

**若加，最小指标集**（避免高基数标签，这是 prom-client 的常见坑）：
```
xianyu_cycles_total{task}                     轮询次数
xianyu_scanned_total{task}                    扫描条数
xianyu_matched_total{task}                    命中条数
xianyu_push_attempts_total{task,channel,result}   推送尝试（result=ok|retryable|unrecoverable）
xianyu_outbox_pending                         待投递队列长度   ← 最有价值的一个
xianyu_outbox_oldest_age_seconds              最老待投递的年龄   ← 直接反映「推送卡住了」
xianyu_last_success_timestamp{task}           心跳             ← 可直接做告警规则
```
**注意**：`task` 和 `channel` 是低基数（用户自己配的几个），可以放标签；**绝对不要把 `item_id` 放标签**。

#### 2.4.4 参考：ntfy 的可观测性设计

`ntfy` 的配置文档里有独立的 **Health checks**、**Monitoring**、**Profiling** 章节，并有 `/v1/health` 端点。🟢（读自 [docs.ntfy.sh/config](https://docs.ntfy.sh/config/) 目录结构）

### 2.5 配置管理（含「界面手里的副本过期把别处改动回滚」）

#### 2.5.1 问题的本质

我们踩的坑是典型的 **lost update**：

```
时刻 T1  界面读到 config.json (rev=A)，在内存里持有一份副本
时刻 T2  用户手工改了 config.json 的某个键   → 磁盘变成 rev=B
时刻 T3  用户在界面上改另一个键，界面用「副本 + 改动」整体写回 → 覆盖掉 T2 的改动  ❌
```

我们现在改成「从磁盘重读、只改一个键」，这**部分**解决了问题（把窗口从「用户思考时间」缩短到「读-改-写」的毫秒级），但**没有根除**：两个并发请求仍会互相覆盖。

#### 2.5.2 🟢 成熟模式 A：Home Assistant 的 config entry（UI 是唯一写者）

> 📎 [Home Assistant Developer Docs — Config entries](https://developers.home-assistant.io/docs/config_entries_index/)
> Config entries are configuration data that is persistently stored by Home Assistant. **A config entry is created by a user via the UI.**

> 同文档，Modifying a config entry
> A `ConfigEntry` object, including the data and options, **must never be mutated directly by integrations**, instead integrations must call `async_update_entry`

> 同文档，Migrating config entries to a new version
> If the config entry version is changed, `async_migrate_entry` must be implemented to support the migration of old entries.

> 同文档，Lifecycle 表（部分）
> | State | Description |
> |---|---|
> | setup error | An error occurred when trying to set up the config entry. |
> | **setup retry** | A dependency of the config entry was not ready yet. Home Assistant will automatically retry loading this config entry in the future. **Time between attempts will automatically increase.** |
> | migration error | The config entry had to be migrated to a newer version, but the migration failed. |

**三个可抄的点：**

1. **单一写者 + 单一真相源**。配置持久化在 `.storage`（由框架管理），YAML 只是导入入口，**不参与运行时写入**。这从结构上消除了「两个写者」。
2. **禁止直接 mutate，必须走 `async_update_entry`**。所有写入经过同一个函数 → 该函数是加校验、加锁、加版本号的唯一位置。
3. **`version` + `async_migrate_entry`**：配置格式变更时有**显式的迁移函数**，而不是靠「读到未知字段就当没有」。我们 `store.mjs` 有 `STATE_VERSION` 但**没有迁移函数** —— 目前是「版本不匹配就抛错并备份」，这对状态文件可接受（最坏重置），但**对配置文件不可接受**（用户手写的关键词会丢）。
4. **生命周期状态机**：`setup error` / `setup retry`（**退避递增**）/ `migration error` 都是**一等状态**，在界面上可见。我们的任务也可以有类似的显式状态（`ok` / `cooling` / `risk-control-paused` / `auth-expired`），而不是只在日志里。

#### 2.5.3 🟡 成熟模式 B：原子写 + 校验后再生效（两条铁律）

> 📎 [Runtime config hot-reload without restarting the service](https://www.bigiron.cc/guides/runtime-config-hot-reload-without-restarting-the-service)（二手指南）
>
> - **Atomic write or bust.** Write to a temp file and `rename()`; never edit a watched config in place, or you'll occasionally reload a half-written file.
> - **Validate before reload.** `nginx -t`, `sshd -t`, `caddy validate` first; a bad config should leave the old one running, never take the service down.
> - **Watch the directory, not the file**, for atomically-replaced configs (and Kubernetes ConfigMap symlinks), because the inode changes on swap.
> - A **failed reload that kept the old config is alertable** - the most dangerous reload outcome is the silent one, where the new config was rejected and nobody noticed the service is still running yesterday's settings.
> - Tag logs with the **config checksum** each process is running... when one instance behaves differently, the checksum tells you instantly that it didn't get the update everyone else did.

**对我们直接适用的四条：**

| 铁律 | 我们的状态 |
|---|---|
| 原子写（temp + rename） | ✅ `store.mjs` 已有；**配置文件写入也应该用同一套** |
| **校验后再生效** | ✅ 我们有 `validateChannels()`（`notify.mjs:92`）+ 任务表单校验。**但要确保：校验失败时旧配置继续生效，且界面明确显示「已拒绝」** |
| **watch 目录而非文件** | ⚠️ 若将来做「改文件自动热生效」，必须 watch 目录（因为 rename 会换 inode）。**我们现在没有文件监视，所以还踩不到这个坑** |
| **失败的 reload 必须可告警 + 日志带配置 checksum** | ❌ **缺**。建议：每次 `config.mjs` 加载成功后在日志里打 `config rev=<n> sha256=<前8位>`，界面顶部也显示当前生效的 rev |

#### 2.5.4 成熟模式 C：乐观并发控制（CAS）—— 这才是「回滚」的正解

这是分布式系统里解决 lost update 的标准做法，也是我们真正缺的一块：

```
1. config.json 里存一个单调递增的 revision（或内容内容的 sha256）
2. 界面加载时拿到当前 revision，每次提交都带上 ifRevision
3. 服务端：读取磁盘 → 比较 revision
     一致   → 应用改动，revision+1，原子写回
     不一致 → 返回 409 Conflict（不写入！），响应体带当前最新配置
4. 界面收到 409 → 提示「配置已被其他地方修改」+ 展示差异 + 让用户重新确认
```

**为什么这比「从磁盘重读、只改一个键」更好**：我们的做法缩小了窗口但没关闭它；CAS 让**冲突变成一个显式的、用户可见的事件**，而不是静默的数据丢失。

**实现成本很低**：`config.mjs` 加一个 `revision` 字段 + 写入前比对 + 一个 409 分支 + 界面一个「重新加载」按钮，大约 **半天**。

#### 2.5.5 🟢 附：ntfy 的「声明式配置 + 数据库」双轨制

ntfy 的做法值得一提（读自 [官方配置文档](https://docs.ntfy.sh/config/)）：

> Users added declaratively via the config file are marked in the database as "provisioned users". Removing users from the config file will **delete them from the database** the next time ntfy is restarted.

**这是一个明确的、有文档的优先级规则**：配置文件是**声明式真相源**，数据库是它的投影；重启时以文件为准。

**对我们的启发**：如果我们既想支持「手改 `config.json`」又想支持「界面编辑」，就必须**明确声明谁是真相源**。两个合理选择：

| 方案 | 真相源 | 适用 |
|---|---|---|
| **A. 文件是真相源** | `config.json`；界面只是编辑器，每次写完立刻落盘并重读 | ✅ **适合自托管 + 有 git 管理的用户**（我们的场景）。CAS 版本号验证必须加。 |
| **B. 运行时存储是真相源** | 一个 `.storage` 式的内部状态库；`config.json` 只在**首次启动**导入 | ✅ 适合「界面为主」的用户，但**手改文件会被忽略**，必须显式告知 |

**我们的选择应该是 A**，因为目标用户会 SSH 进去改文件、也会用 git 管配置。那么就必须接受「文件随时可能被外部改动」，**CAS 是必需品而不是可选项**。

### 2.6 Web 控制台

#### 2.6.1 单文件零依赖 vs 前后端分离

我们的现状：`src/web/index.html` **162KB 单文件**，零依赖、零构建，由 `src/server.mjs` 提供服务。

| 维度 | 单文件零依赖（我们） | 前后端分离 / SPA |
|---|---|---|
| **部署** | ✅ 拷一个文件就能跑；`node src/cli.mjs web` 即用 | ❌ 需要 `pnpm build`、产物目录、静态托管配置 |
| **可审计** | ✅ 用户能直接打开看有没有偷传数据 —— 对**涉及 cookie/登录态的工具**这是巨大的信任优势 | ❌ 压缩后的 bundle 无法审计 |
| **依赖风险** | ✅ 供应链攻击面 ≈ 0 | ❌ 一个 `npm install` 可能引入几百个包 |
| **离线/内网** | ✅ 完全离线可用 | 🟡 取决于构建产物是否内联 |
| **开发体验** | ❌ 无类型检查、无组件复用、162KB 后开始难维护 | ✅ 类型 + 组件 + HMR |
| **测试** | ❌ 难（我们的 `check-console-*.mjs` 是 DOM 契约测试，属于自制方案） | ✅ 有成熟测试生态 |
| **体量上限** | 🟡 大约 200~300KB 后到达临界点 | ✅ 无限 |

**业界的选择分布**（🟢 基于我读到的文件结构 / ⚪ 基于印象）：

| 项目 | 形态 | 评价 |
|---|---|---|
| **ntfy** | 服务端渲染 + vanilla JS 单页 | 和我们的路线一致 |
| **changedetection.io** | Flask + Jinja 模板 + 少量 JS（`templates/`、`static/`），**渐进增强** | 比我们更"分文件"，但同样零构建 |
| **prometheus/alertmanager** | Go template + 静态资源，零构建 | 同路线 |
| **Uptime Kuma** | Vue SPA（有构建步骤） | 功能最丰富的那个，也最重 |
| **Home Assistant** | 独立前端仓库 + 完整构建链 | 体量决定 |

**结论**：**我们的路线在自托管场景是正确的，不要换。** 但有两条改进建议：
1. **把 162KB 的 `index.html` 按功能拆成几个文件**（任务表单 / 通知渠道 / 日志 / 命中历史），用 ES module 引入。仍然是零构建、零依赖，但可维护性会显著提升。
2. 保持**「核心功能不依赖 JS 也能看到信息」**的渐进增强原则（比如命中历史先渲染成 HTML 表格）。

#### 2.6.2 危险操作的确认：抄 friction ladder

我们已经有一些危险操作（删除任务、清空历史、手动重推、清空去重表）。这里有一个**非常成熟、可直接照搬**的框架。

> 📎 [destructive-confirmation 模式简报](https://github.com/adamforrester/knowledge-base/blob/main/patterns/destructive-confirmation.md)（二手，但是一份结构化的设计规范）
>
> The field's hard-won lesson is that **most destructive actions should be undoable, not confirmed**: a confirmation that fires too often becomes motor-memory noise, dismissed without reading, so it protects nothing and the one time it mattered, it failed.

**摩擦阶梯（原文，直接抄成一张决策表）：**

| 级别 | 场景 | 做法 |
|---|---|---|
| **L0 琐碎**（高频、可恢复、无足轻重） | 切换开关、改间隔 | 立即执行，**无确认** |
| **L1 可恢复**（软删除） | 删除一条命中历史 | 乐观执行 + **Undo toast** |
| **L2 不可逆、单条** | 删除一个监控任务 | 简单确认对话框 |
| **L3 灾难性**（大范围影响） | **清空全部去重表**、清空全部历史 | **type-to-confirm**（要求输入资源名） |
| **L4 致命** | —（我们不涉及） | MFA / 二次审批 |

**四条硬性规则（原文摘录，全部可直接应用于我们的界面）：**

> **NEVER autofocus the destructive button.** Focus the **cancel/safe** option (or the dialog/its heading) so a reflexive Enter/Space can't destroy.

> Title is the **specific question**; body states the **consequence, scope, and irreversibility**.

> **Action-specific verbs** — "Delete 3 files," "Discard draft," "Deactivate account" — never "OK/Yes/Confirm."

> **Undo-toast timing problem** — an auto-dismissing toast is an a11y trap: the Undo must be **announced** (polite live region) *and* reachable before it vanishes. **Pause the toast's expiration timer the moment it receives keyboard focus or hover**

> **Bulk:** `IF acting on N items` → state the **exact count in the title** ("Delete 14 files?") and **enumerate cascading consequences** in the body

**对我们的具体映射：**

| 我们的操作 | 当前摩擦 | 建议级别 |
|---|---|---|
| 手动重推一条命中 | 点击即推 | **L0/L1**（可恢复 —— 大不了再推一次；但要注意对用户的 Telegram 是重复消息，所以至少加个轻提示） |
| **批量重推** | 无此功能 | L2 + **标题写准确数量**「重推 14 条命中？」 |
| 删除一个任务 | 应有确认 | L2，「删除任务『相机』？」+ 说明「命中历史会保留，去重表会保留」 |
| **清空去重表** | 危险 | **L3 type-to-confirm**：要求输入 `清空` 或任务名 |
| 清空命中历史 | 危险且不可逆 | **L2 或 L3** |

**特别注意「动词标签」这条**：我们的按钮如果是「确定/取消」，应该改成「删除任务 / 取消」。这是零成本改进。

#### 2.6.3 乐观更新的纠正

> 📎 同上文档
> **Path A — the undo path (default, reversible).** *Intent* → *optimistic execution* ... **or** Undo → an abort signal cancels the queued job → the item reappears (optimistic revert) → a success toast confirms restoration. The user is never *blocked*; the safety is the reversal window, not a gate.
>
> An *illustrative* timeline (the orchestration must avoid race conditions): T=0 item unmounts; T≈50ms toast renders + job enters the queue; T=50ms–~7s the user has full agency elsewhere while the toast persists; T≈7s toast begins exit; T≈7.3s toast unmounts + the queue **locks** the job (no late abort); T≈7.5s the database purge runs.

**关键工程洞察**：乐观更新**必须有「队列锁」**，否则用户点了 Undo 但后台已经执行完了 → 界面显示已恢复，实际没恢复。

**对我们的建议**：**不要引入乐观更新**。我们现在的「每行可手动重推」是**悲观但正确**的模型 —— 点击 → 等服务端返回 → 用返回结果更新该行状态。在「推送」这个场景里，重复推送的代价（用户手机上多一条消息）**高于**多等 500ms 的代价。

**但可以借鉴「明确的失败回滚」**：手动重推失败时，**行状态必须回退到「未推送」并显示错误原因**，而不是乐观地标记成成功。

#### 2.6.4 一个我们没有但值得考虑的功能

回到 §2.1：如果实现了 outbox，界面上就应该有一个 **「待投递队列」视图**：

```
待投递 3 条：
  · 相机  ¥1200  佳能 EOS R8...   渠道: 钉钉   已重试 4 次  下次 2 分钟后  最后错误: HTTP 429
  · 相机  ¥980   索尼 A7C...      渠道: Telegram 已重试 1 次  下次 30 秒后
  · 镜头  ¥4500  适马 24-70...    渠道: 钉钉   不可恢复 ⚠️  HTTP 401 token 无效  [重新配置]
```

这一个视图就同时解决了：可观测性（能看见积压）、人工补偿（可手动重推）、以及「通道配置错了」的可诊断性。**性价比极高。**

## 5. 按性价比排序的建议清单

排序依据：**（解决问题的严重程度 × 出现概率）÷ 工作量**。

---

### 🥇 第 1 名：按渠道记账 + 轻量 outbox —— 修掉真实的静默丢推送

**优先级：最高（这是一个已存在的 bug，不是改进）**

| 项 | 内容 |
|---|---|
| **解决什么问题** | 多渠道路由下，**失败的那个渠道永久收不到这条命中**（`src/monitor.mjs:482` 用 `results.some(r => r.ok)` 判断是否记账）。另外，失败告警本身（`src/monitor.mjs:300`）也走同一条不可靠路径，「登录失效」「风控被拒」这类最需要送达的告警会丢。 |
| **抄谁** | 🟢 Alertmanager 的 `RetryStage` + `nflog`（§2.1.1）：**渠道进去重键**、**投递成功后才 ack**、**`NotifyVerdict` 区分可重试/不可重试**、**`max(backoff, Retry-After)`**。🟡 LENKIN233 的 `idempotency_key` + `possible_duplicate` 信号。 |
| **具体做法** | ① 记账键从 `item.id` 改为 `item.id + ':' + channel`；② 新增 `outbox` 结构（字段见 §2.1.6），与 `seen` 在同一次 `store.save()` 中原子落盘；③ 投递循环按 `next_attempt_at` 取件、按渠道独立投递、成功才标 `sent`；④ `toResult` 增加 verdict 分类：`429`/超时/5xx → 可重试，`401`/`400` → `unrecoverable` + 立即告警。 |
| **工作量** | **中，约 1.5~2 人日**。`store.mjs` 加 schema（~80 行）+ `notify.mjs` 加 verdict（~40 行）+ `monitor.mjs` 改 dispatch（~120 行）+ 单测（~100 行）。 |
| **风险** | 低。可以**分两步走**：先只改记账键（半天，立刻修掉丢推送），再加完整 outbox。 |
| **附带收益** | 顺带解决「崩溃窗口」的语义模糊（有了 `possible_duplicate` 信号），并为 §5.5 的「待投递队列」界面铺路。 |

---

### 🥈 第 2 名：任务心跳 + 错轮告警 —— 补上完全无告警的盲区

| 项 | 内容 |
|---|---|
| **解决什么问题** | 我们现在**所有告警都在 `catch` 里触发**。如果任务悄无声息地卡住（`fetch` 永不返回、事件循环被阻塞、定时器被吞），`catch` 永不执行 → **零告警，界面上也看不出异常**。这是当前唯一完全没有覆盖的故障模式。 |
| **抄谁** | 🟢 healthchecks.io 的 `Period` + `Grace Time` 模型（§2.4.2，官方文档原文）。🟡 Gatus 的 alert 状态机（`TRIGGERED` / `RESOLVED`）——**恢复时也发一条通知**，我们现在没有恢复通知。 |
| **具体做法** | ① 每个任务记录 `lastCycleCompletedAt`（内存 + `store.totals`）；② 独立的轻量检查（每 30s）扫描：`now - lastCycleCompletedAt > intervalSeconds + graceSeconds` → 判定错轮 → 走 outbox 告警；③ 恢复时发一条「已恢复正常」；④ 在 Web 控制台顶部显示每个任务的心跳状态。 |
| **工作量** | **小，约 0.5~1 人日**。约 80 行代码 + 一个配置项 `graceSeconds`（默认取 `max(60, intervalSeconds)`）。 |
| **风险** | 极低。纯增量，不改动现有流程。 |
| **为什么排第 2 而不是第 1** | 它是一个**从未发生过的**故障模式（概率低），但一旦发生完全不可见（严重性高）。而第 1 名是**已经存在**的 bug。 |

---

### 🥉 第 3 名：配置 `revision` + CAS（409 冲突）—— 根除「界面回滚别处改动」

| 项 | 内容 |
|---|---|
| **解决什么问题** | 我们踩过的「界面手里的副本过期把别处改动回滚」。现在的「从磁盘重读、只改一个键」把窗口从「用户思考时间」缩短到毫秒级，但**没有根除并发覆盖**。 |
| **抄谁** | 🟢 Home Assistant 的 config entry 模型（§2.5.2）：**单一写者 + 禁止直接 mutate + `version` 迁移**。🟡 热重载指南的两条铁律（§2.5.3）：**原子写**、**校验后再生效**、**日志带 config checksum**。 |
| **具体做法** | ① `config.json` 加 `revision`（数字或内容 sha256）；② 界面加载时记录 revision，提交带 `ifRevision`；③ 服务端比对，不一致 → **返回 409 + 当前最新配置**，不写入；④ 界面收到 409 → 显示「配置已被其他地方修改」+ 差异 + 让用户重新确认；⑤ 写入用「temp + rename」（复用 `store.mjs` 的模式）；⑥ 加载成功后日志打 `config rev=N sha256=xxxx`，界面顶部显示当前生效 rev；⑦ 校验失败时**保留旧配置并在界面明确提示「已拒绝」**（不能静默）。 |
| **工作量** | **小，约 0.5~1 人日**。 |
| **风险** | 低。但要注意**迁移**：老的 `config.json` 没有 `revision` 字段，加载时要补一个默认值（并提供 `revision` 缺失时的兼容读取）。 |
| **额外价值** | 一旦有了 revision，就顺手获得了「当前生效的是哪一版配置」这个可观测性，能直接诊断「为什么我的改动没生效」。 |

---

### 第 4 名：退避加抖动 + 熔断/半开探测 —— 避免风控期惊群和持续撞墙

| 项 | 内容 |
|---|---|
| **解决什么问题** | ① 退避值 `cooldownSeconds * 2`（`src/monitor.mjs:269-272`）**没有抖动** → 多任务同时失败时会在同一时刻集体重试（惊群），在风控期这是最坏的行为；② 缺 **L4 全局熔断**：多个任务同时被风控时，我们仍会各自按自己的冷却去试探；③ 缺 **L6 半开探测**：冷却结束后直接用正常间隔重试，而不是「单次试探」。 |
| **抄谁** | 🟢 Scrapy AutoThrottle（§2.3.1，特别是 **L120-125 的「错误响应不得降低延迟」**这条正反馈陷阱）；🟢 got 的退避公式 + 抖动（§2.3.2）；⚪ AWS Full Jitter；🟡 Usagi-org 的 `TASK_FAILURE_PAUSE_SECONDS`（**暂停任务**而非继续撞墙）。 |
| **具体做法** | ① 退避值乘 `(0.5 + random*0.5)` —— 一行改动；② 增加全局熔断状态：N 个任务在窗口内同时风控 → 暂停所有任务并告警；③ 冷却结束后的第一次请求用「单次试探」（若失败则重新进入长冷却，而不是恢复常规节奏）。 |
| **工作量** | 抖动本身 **15 分钟**；全局熔断 + 半开探测 **约 1 人日**。**可以只做抖动 + 试探（半天）拿到 80% 收益。** |
| **风险** | 中。熔断状态机容易写错（比如误判恢复）。建议加足日志。 |

---

### 第 5 名：待投递队列视图 + 手动补偿 —— 把可靠性变成可见、可控

| 项 | 内容 |
|---|---|
| **解决什么问题** | 有了 outbox 之后，需要让人**看见**积压、**手动干预**卡死的投递。同时改善界面上的危险操作。 |
| **抄谁** | 🟢 ntfy 的「服务端保留 + 客户端补收」思路（§3.1）；🟡 destructive-confirmation 的 friction ladder（§2.6.2）。 |
| **具体做法** | ① 界面新增「待投递队列」视图（`pending` / `failed` / `unrecoverable` 三组，显示重试次数、下次时间、最后错误）；② 每行支持「立即重推」；③ 危险操作按 friction ladder 重做：**清空去重表 → type-to-confirm**；**按钮改动词标签**（「确定」→「删除任务」）；**确认框不 autofocus 危险按钮**；④ 批量重推时标题写准确数量（「重推 14 条命中？」）。 |
| **工作量** | **中，约 1~1.5 人日**（前端为主，单文件 `index.html` 需拆分）。 |
| **风险** | 低。但前端 162KB 单文件会变难改，建议**先按功能拆分**（§2.6.1 建议 1）。 |

### 🚫 明确不建议做的

| 项 | 原因 |
|---|---|
| **布隆过滤器做去重** | 假阳性 = 永久漏报，且不支持删除。我们现在 `limit=20000` 的 JSON 只有约 1MB，省这个空间毫无意义。 |
| **Prometheus + Grafana** | 单进程、自托管、已有控制台。收益（长期趋势）低于成本。**若要做，先做第 2 名的心跳告警**。要加时用 §2.4.3 的最小指标集，注意别把 `item_id` 放进标签。 |
| **多进程 / 多账号池** | 会立刻引入跨进程限流、跨进程去重、跨进程 outbox 三个新问题。除非确实需要，否则单进程是优势。 |
| **乐观更新 UI** | 在推送场景里，「重复推送」（用户手机多一条消息）的代价高于「多等 500ms」。保持乐观更新反而增加复杂度。 |
| **抄 RSSHub 的任何代码** | AGPL-3.0，与我们的 MIT 冲突。 |
| **盲目重试超时请求** | 引用 LENKIN233 的原则：**未收到响应不等于未送达**。超时后应标记 `possible_duplicate` 并**有节制地**重试，而不是无脑重发。 |
