# 闲鱼（Goofish / 闲鱼 / 2.taobao.com）开源项目调研报告

> **调研目的**：一个自建闲鱼关键词监控工具（Playwright 驱动有头 Chrome 打开 `www.goofish.com/search`，**监听页面自身发出的请求**取结果，不复刻任何签名）目前遭遇：同一页面加载里 8 个 mtop 接口全部 SUCCESS，**只有 `mtop.taobao.idlemtopsearch.pc.search` 返回 `RGV587_ERROR::SM::哎哟喂,被挤爆啦`**；处罚链接为 `bixi.alicdn.com/punish/...&action=deny`，页面显示「亲，访问被拒绝」，**无可操作验证项**；**同账号在手机 App 搜索完全正常**；已排除换手机 UA、去掉 `--enable-automation`。
>
> **核心问题**：有没有开源项目用**别的链路**把闲鱼搜索跑通了？

## 1. 关键结论速览（TL;DR）

1. **没有任何开源项目能直接解决你的局面。** 没有任何项目提供「网页搜索接口被 deny 时切换到的第三条可用链路」。社区一致的做法是**等冷却 + 重新下发风控 cookie**，而不是换链路绕过。

2. **最重要的技术区分（这决定了你的选项范围）**：闲鱼有**两套完全不同的签名族**：
   - **网页/PC mtop**：`sign = md5(_m_h5_tk_token + "&" + t + "&" + appKey + "&" + data)` —— 纯 MD5，**不需要** `x-sign`/`x-mini-wua`/`x-sgext`/`x-umt`。
   - **App mtop**：`x-sign` / `x-mini-wua` / `x-sgext` / `x-umt` + `x-devid`/`x-utdid`。
   
   你监听的那个 `pc.search` 属于**第一套**。所以「自己实现签名绕过去」对你这条路**没有增量意义**（你不缺签名，浏览器已经替你签了）。

3. **App 协议路线基本不覆盖搜索**。高 star 的 App 逆向项目（`shaxiu/XianyuAutoAgent` 9.2k★、`zhinianboke/xianyu-auto-reply` 7.3k★）都是 **IM/自动回复/订单**方向。全网**没有任何一个项目提供了可用的 App 端搜索 API 签名生成器**；只有一个 6★ 的研究仓库捕获了 App 搜索的请求参数**值**（非生成器）。

4. **一个具体、廉价、可立刻验证的线索**：`11273/goofish-client` 有一个专门修复 **search 接口报错**的提交，方法是**在 cookie 缺失时自动生成 `cna`**。【源码确认，见 §3.5】

5. **另一个结构性线索**：多份独立材料把 `mtop_partitioned_detect` 和 `x5sec` 列为风控关键 cookie。【README/源码确认】结合你「8 个接口通、只有 pc.search 被拒」的表现，**我推测**（明确标注为推测）风控决策可能是**按接口**下发的，而非按账号整体封禁。这值得优先验证。

### 3.2 关键澄清：**(a) 与 (a′) 是两套不同的签名族**

这是本次调研最重要的技术发现，直接改变你的选项判断。

**【源码确认】`11273/goofish-client`** —— `src/utils/sign.ts`：

```ts
export function generateSign(params: SignParams): string {
  const { appKey, t, data, token } = params;
  const signStr = `${token || ''}&${t}&${appKey}&${data}`;
  return md5(signStr).toString();
}
```
且 token 取自 `_m_h5_tk` cookie 的下划线前缀（`getTokenFromCookie`）。**纯 MD5，全文无 `x-sign`/`x-mini-wua`/`x-sgext`/`x-umt`。**

**【源码确认】同仓库** `src/constants/api.mtop.ts` —— 确认搜索走的就是你那个接口：

```ts
BASE_URL: 'https://h5api.m.goofish.com',
APP_KEY: '34839810',
SEARCH: { SEARCH: 'mtop.taobao.idlemtopsearch.pc.search' },
```

**【README 确认】`yuan71058/XianYuApis-GO`** 也写明同一套：
> 签名生成: MD5(token + "&" + timestamp + "&" + appKey + "&" + data)

**【搜索结果 + 原文确认，掘金】** [《闲鱼商品搜索爬虫：从签名算法到反爬机制的完整逆向与实现》](https://juejin.cn/post/7557342643177979930) —— 针对 `mtop.taobao.idlemtopsearch.pc.search` 独立复现了同一套算法：`sign = MD5(token + "&" + timestamp + "&" + appKey + "&" + data)`，`appKey=34839810`，token 来自 `_m_h5_tk`。

**结论**：网页搜索接口**不需要** App 签名。你的工具「不复刻签名、只监听浏览器请求」这个设计**本身没有问题** —— 签名不是你的瓶颈。

**关键判断**：
- **【推测】** 该仓库捕获的 `data` 载荷含 `"keyword":"手机"`, `"pageNumber":2`, `"rowsPerPage":99`, `"sortField":"time"`, `"searchReqFromPage":"xyHome"` —— **从字段看我判断这是一次 App 端商品搜索请求**。但**README 未声明 API 名**（未出现 `idlemtopsearch.search` 字样），所以「这是 App 搜索接口」是**我的推断，不是原文结论**。

### 5.2 三个最值得你借鉴的设计

**① `LENKIN233` 的 durable outbox + 幂等键（最重要）**

它的设计解决了「**监控去重」与「通知投递」之间的原子性问题**，原文：
> 新商品会和 seen ID 在同一原子提交中写入 durable outbox；适配器通过 `task outbox list` 读取，复用 `idempotency_key`，仅在外部投递确认成功后执行 `task outbox ack`。

> 若发送超时、发送中取消或本地 ack 无法确定，事件保留并返回 `possible_duplicate: true`；**未收到响应不等于未送达，不要盲目重试。**

> 重复通知优于已提交 ID 导致的永久漏报。

**为什么值得借鉴**：你的监控在风控期会频繁失败重试。如果「已标记为已读」和「已推送」不在同一事务里，风控恢复后就可能**漏报**（因为 ID 已被记入去重集合但没推送出去）。它的**显式 at-least-once 语义 + 幂等键**是正确的解法。

**② `Usagi` 的「风控 → 轮换 → 重试」闭环**

其 README 的工作流（mermaid 原文）：
```
C[任务: 搜索商品] --> L{触发风控/异常?};
L -- 是 --> M[账号/代理轮换并重试];
M --> C;
```
配置项包括 `PROXY_ROTATION_ENABLED` / `PROXY_ROTATION_MODE` / `PROXY_POOL` / `PROXY_ROTATION_RETRY_LIMIT` / `PROXY_BLACKLIST_TTL` / `TASK_FAILURE_THRESHOLD` / `TASK_FAILURE_PAUSE_SECONDS` / `TASK_FAILURE_GUARD_PATH`。

**对你**：**多账号池**是社区公认的应对手段。但注意其 README 的「账号管理」是**导入登录态文件**（`state/acc_1.json`），而非自动登录 —— 意味着**每个账号仍需人工在浏览器里养出干净会话**。

**③ `voltwake` 的「stdout 结构化契约 + 哨兵标记」**

它用三个标记让任意调度器/agent 消费：
```
--- NEW_ITEMS_JSON ---
[ ... ]
--- END_NEW_ITEMS_JSON ---
--- COOKIE_EXPIRED ---
```
**好评点**：把「有新品」和「需要人工介入」用**独立哨兵**区分，避免把风控失败伪装成「本次没有新品」。`LENKIN233` 也有同样的设计原则：
> 失败、登录跳转和风险控制会明确返回错误，**不会伪装成"没有商品"**。

**这条对你直接适用** —— 你现在的工具在 RGV587 时**必须硬失败**，绝不能让上层以为「本次没搜到」。

## 8. 最终判断：有没有项目能直接解决你的局面？

### 结论：**没有。一个都没有。**

我核查了 253 个仓库，其中直接相关（搜索链路 / RGV587）的 10 个我逐一读了 README、源码或 Issue 原文。**没有任何一个项目提供「当网页搜索接口被 deny 时，可切换到的第三条可用链路」。**

### 为什么没有？四条相互独立的理由

**① 你遇到的不是「反爬技术难题」，而是「风控拒绝」。二者解法相反。**

所有项目的技术手段（签名、UA、导航方式、自动化标记）解决的是**「让请求看起来合法」**的问题。而你的请求**本来就合法** —— 浏览器自己发的、签名正确、其他 8 个接口在同一页面同一会话里全部 SUCCESS。**例外只发生在 `pc.search` 这一个接口上**。这说明问题不在你的客户端，而在**服务端针对该接口对该会话下发了拒绝**。开源项目里所有"绕过"技巧都是针对前者设计的，对后者无效。

**② 「同账号 App 正常」这件事本身，恰恰说明换 App 链路不是捷径。**

- 你的 App 走的是 `mtop.taobao.idlemtopsearch.search` + **`x-sign`/`x-mini-wua` 签名族 + 真机设备指纹**（`x-devid`/`x-utdid`/`imei`）。
- 你的网页走的是 `pc.search` + **MD5 签名**。
- 这是**两个独立的接口、两套独立的签名、两套独立的风控画像**。App 通过**不代表**网页应该通过，也**不能**用来给网页"背书"。

而且 **【源码/README 确认】全网没有可用的 App 搜索 `x-sign` 生成器**：
- `bytesFighting/idlefish-xianyu-x-sign-and-request-params`（6★，无许可证，2025-03 停更）**只有捕获的签名字符串和请求参数值**，没有生成算法。签名字符串无法反推。
- `bytesFighting/idlefish_xianyu_spider-crawler-sender`（304★，MIT）虽然涉及 x-sign 与 unidbg，但**我未确认它实现了 App 搜索接口**，且 unidbg 复现 `sgmain.doCommandNative` 是**极高成本**工程（需要 App 样本 + 原生 so 逆向 + 设备指纹模拟）。
- 即使你走通了，你会得到**第三个**受风控管辖的路径，而不是一个"安全"的路径。

**③ 唯一记录 `action=deny` 类无验证项场景的项目，答案是「无解」，且实测被证伪。**

- 【Issue 确认】`cv-cat/XianYuApis` Issue #36：**同一账号浏览器正常、程序路径被拒**；验证 URL 跳转到 `.../_____tmd_____/undefined`「未能完成该验证」。**状态 open，唯一回复是「同问」。**
- 【Issue 确认】`IAMLZY2018/xianyuapis` Issue #4：同错误码。有人尝试加 PyExecJS 修复，回复原文是「**然后同样被挤爆了**」。**至今 open。**
- 【Issue 确认】`qOeOp/goldfish-agent` Issue #13：完全相同的 `RGV587_ERROR`（HTTP 200 + 业务错误）。**0 条回复。**
- `yuan71058/XianYuApis-GO` 的 `CaptchaHandler` 方案依赖 `data.url` 中有**可完成的验证项** —— 你的 `action=deny` 场景会卡死在「用户完成验证」这一步。

**④ 社区共识是「冷却 + 重新下发 cookie」，且明确反对绕过。**

- `fancyboi999/goofish-cli`：RGV587 属**服务端风控，本地解不了**；流程是**不重登录** → 浏览器正常浏览 3-5 分钟让 `x5sec` 和 `mtop_partitioned_detect` 下发 → 重导 cookie；仍失败则**停手 2-6 小时**；`FAIL_SYS_ILLEGAL_ACCESS` 明确标为「自动化救不了，必须人工介入 ❌」。
- `LENKIN233/xianyu-monitor-skill`：「RGV587 时让请求/会话冷却……**不重新登录、不换代理，也不再用 `--headed` 尝试**」；「**不要循环尝试或加入反检测绕过**」。
- `voltwake/xianyu-monitor`【源码确认】：把 RGV587 直接归类为「**Cookie 可能过期**」。
- 掘金文章：推荐「**加入随机延时**」+ 固定 Referer。

**没有任何一个项目的结论是「换一条链路就行」。** 最激进的方案（Usagi 的多账号+代理池轮换）也只是**换身份重试**，而不是**绕开拒绝** —— 而且它的每个账号仍需人工在浏览器里养出干净会话。

### 那么你该做什么？三个有依据的下一步

**第 1 步（最高性价比，立刻可做）：确认 `cna` 与风控 cookie 的存在性。**

- 【源码确认】`11273/goofish-client` 有一个**专门修复 search 接口报错**的提交，做法是在 cookie 缺失时补 `cna=随机24字符`。
- 【原文确认，掘金】能成功取到数据的 Cookie 集里包含 `cna=...` 和 **`mtop_partitioned_detect=1`**。
- 【README 确认】`goofish-cli` 列出 4 个风控关键 cookie：`x5sec`、**`mtop_partitioned_detect`**、`isg`、`l`。
- **行动**：把你 Playwright 抓到的 `pc.search` 请求头里的 cookie **逐项对照**上面 4+1 项。**特别检查 `mtop_partitioned_detect` 和 `cna` 是否存在、是否为空。**
- **【推测】我的假设**：Chrome 的存储分区（storage partitioning）行为可能影响 `mtop_partitioned_detect` 相关 cookie 的携带；Playwright 默认新建的 browser context 与「日常浏览器 profile」在分区状态上可能不同。结合「8 个接口通、只有 pc.search 被拒」，**风控可能是按接口 + 按分区 cookie 状态判定的**。**这只是假设，需要你用抓包数据证实或证伪。**

**第 2 步：按社区共识做「冷却 + 养 cookie」，而不是继续对抗。**

- **停止**对 `pc.search` 的重试（每次失败都在强化风控画像）。
- **不要**重新扫码登录（会覆盖掉可能还残留 `x5sec` 的 session —— 这是 `goofish-cli` 明确警告的坑）。
- **让该账号在真实浏览器里正常使用 3-5 分钟**（浏览商品详情、翻首页），使 `x5sec` / `mtop_partitioned_detect` 正常下发。
- 导出**包含全部 HttpOnly cookie**（`cookie2`、`sgcookie`）的会话，再重试。
- 若 24 小时不恢复，按 `goofish-cli` 的原文建议「考虑账号本身已被标记」。
- **参考**【README 确认】`LENKIN233` 的做法：把「一次受控搜索是否成功」做成**显式的能力断言**（`search_capability: passed-for-this-run`），而不是把失败静默成「无结果」。

**第 3 步：改架构以降低对单一接口的依赖（长期）。**

- 借鉴 `LENKIN233` 的 **durable outbox + `idempotency_key` + at-least-once** 语义 —— 保证风控期不产生**漏报**。
- 借鉴 `voltwake` 的**哨兵标记**思路，让风控失败显式冒泡（`--- COOKIE_EXPIRED ---`），绝不伪装成「本次无新品」。
- 借鉴 `Usagi` 的**多账号池 + 失败阈值熔断**（README 确认有 `PROXY_POOL`/`TASK_FAILURE_THRESHOLD`/`TASK_FAILURE_PAUSE_SECONDS`），但清楚这需要**多个已养熟的账号**，每个仍需人工登录。
- **【推测】** 如果 `pc.search` 长期被拒，可以考虑**降级到未登录浏览 + DOM 抓取**（`voltwake` 的路线，MIT 可借鉴），代价是**只能看到 6 小时以上发布的商品**（其 README 明确记载），对你的「捡漏」时效性需求可能不可接受。

### 一句话总结

> **开源社区在这件事上的集体答案是：`RGV587` 是服务端风控，客户端的任何"技巧"都无效；正确做法是让会话冷却、重新养出带 `x5sec` 的干净 cookie，然后降频。你缺的不是一条新链路，而是一个干净的会话。** 如果冷却后仍被拒，那么按现有公开记录（Issue #4 / #36 / #13 全部 open 无解），**这个问题在当前开源生态里没有被解决过。**
